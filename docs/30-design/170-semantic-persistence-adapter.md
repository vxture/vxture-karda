## 1. 既有表与新投影的映射

| 内部图谱契约 | 既有事实源 | 适配要求 |
| --- | --- | --- |
| GraphEntity | entity.id/kb_id/kind/name | 固定本体版本的类型映射，不把任意旧 kind 自动当本体类型；同名跨库不合并 |
| GraphAssertion | assertion.content_state/verification_state/superseded_by/valid_until | verificationExpiresAt 单独读取 expires_at；不能等后台把 verified 改成 stale 才阻断过期知识 |
| validFrom | 暂无同义既有列 | as_of 是来源的观察时点，不能直接映射为业务生效时间；无明确有效期时传 null，后续按 DDL 设计增量扩展 |
| GraphEvidence | evidence → span → document | 限 stance=supports；库归属逐跳一致；documentVersion 使用 span.document_version 并与现行 document.active_chunk_version 核对 |
| SourceVersion | document 的活动版本、内容状态及 canonical text | current 由权威活动版本判定；撤回/删除不能用历史发布副本覆盖；textLength 必须来自相同版本的规范原文，不能用摘录或 chunk 长度代替 |
| SemanticRelation | 现有 assertion_mention 只有 mentions/role，尚无完整业务关系 | 新关系表独立保存 source/target/type/schemaRef；不能把同一断言提到两个实体就推断业务边 |
| AuthorizedReadScope | 现有已认证调用身份、关联与可见集、当前租户/角色状态 | 只接受服务端求值；请求中的 kb_ids 只能收窄；权限失效路径须接权威版本，不能仅依赖 300s 缓存 |
| 发布版本 | 当前没有语义发布头 | 本体固定版本、输入快照、人工裁决与候选需形成一致发布边界 |

## 2. 拟增量表和约束

以下为 K1b 的评审对象，不是已执行迁移；最终字段及表数以 210/DDL/Prisma 锁步变更为准。

1. **semantic_schema_version**：不可变版本化定义，namespace/schema_id/version 唯一，definition_hash 与 JSONB 定义绑定。公共定义与租户定义的作用域分别登记，不从一个租户读取另一个租户定义。
2. **semantic_compile_run**：kb_id、schema_version_id、config_fingerprint、input_manifest_hash、来源版本清单、状态与错误；唯一任务键含库、输入和语义配置。断言抽取与向量任务分离，人工裁决 ID 不由重编译重建。
3. **semantic_release**：不可变编译发布记录，含库、本体、run、输入 hash、创建者和创建时点；只引用已校验的候选，不在发布后原地改写内容。
4. **semantic_release_head**：每库当前 release_id 与单调 generation；通过 compare-and-set 切换，失败重试重新读取当前头，不能后到的旧任务覆盖新发布。
5. **semantic_relation**：稳定业务边 ID、库、release、schema、类型、两端 Entity；复合外键或事务校验禁止跨库引用；关系的实例归 Karda。
6. **semantic_relation_assertion**：业务边与支持断言的关联；复合唯一键防重复，所有断言同库且在线读取时重新求有效证据集合；不复制一份脱离原文状态的「永久可信证据」。
7. **semantic_event_receipt**：同一来源事件 ID + 内容指纹 + 处理版本/结果，保证重试幂等；同 ID 异内容拒绝，过期事件留审计但不能推进 head。复用现有事件设施须先核对事件域和授权，不复用平台凭据或事件权威。

依赖影响初期从 relation_assertion → evidence → span 的索引联查得到；如量测证明需物化，加派生依赖索引并明确重建和失效，不将它升级成来源真值。
锚点 id/*_id/created_at 不可改写；新表/列的服务角色授权随增量、列白名单同步 98；不改继承的迁移执行顺序。

## 3. 发布与读取事务

- 编译读取明确来源版本；候选生成期间可以并行，发布前重新核对来源活动版本、本体版本及人工裁决。发生变化即终止此次发布/重排，不覆盖人审结果。
- 一个发布事务写入 release、关系及关联，再按 generation CAS 切 head；任一步失败回滚。不向消费者暴露半份发布。
- 撤回/删除进入权威来源状态；图谱读取在同一数据库一致性快照内校验来源、断言及授权，再遍历业务边。后台索引未更新时也拒绝失效内容。
- 下一次受保护读取必须使用授权撤销后的版本。并发语义以权威状态的读取快照为线性化点，不能用「请求开始时就授权」掩盖长期缓存。
- 确定性推导的前提与规则版本失效必须传到推导边；第一版只发布 asserted，inferred 的证明适配另做独立验收。
- adapter 未准备好或找不到同版本 canonical text 时返回不可用/部分结果说明，不降级成允许全部，也不拿当前原文解释旧偏移。
- 本体或源材料中的指令不影响执行权限；编译模型仅产候选，不能直接调用发布、角色或外部工具。

## 4. 必须跑在隔离数据库的测试

按 owner 调整，数据设计和迁移评审后即可在隔离环境验证；增量脚本需在新库及模拟旧 41 表库各执行两次，K0b 业务质量验收保留到试点前。

## 5. K1b-P1：隔离发布协议实现

`app/kb/semantic/publication.ts` 和 `publication-postgres.ts` 独立实现发布协议，
暂只接受固定前缀的随机测试 schema，不提供环境工厂、HTTP 接口或生产接线。
这一步不要求提前执行 K1b 迁移，也不替代 K0b 的人工复核和独立业务留出集。

- 受信任编译器生成命令，绑定库、事件、预期 generation、来源/人审/本体修订及候选载荷。
  规范 JSON 排序并 SHA256；拒绝非 JSON、访问器、循环、超深及超过 256 KiB 的命令。
  发起数据库等待前复制输入，调用者随后修改候选不能改变此次发布。
- 同库事务级 advisory lock 覆盖首次无 head 情况；读取 head 并比较 generation，
  最后仍用条件更新切头。同事件同指纹只回原回执，同 ID 异内容拒绝；旧任务不能覆盖新 head。
  重复事件的回执仅证明历史处理成功，不代表现行版本或当前读取权限。
- 来源、本体、人审与发布权限由构造时注入的权威读取器求值，必须在同一事务持有相应行锁至提交。
  测试读取器锁定一条隔离 revision 行；它不是产品来源、角色或 OBO 适配器。
- release、head 和 receipt 同事务写入；末步失败回滚全部。不同库分别保留事件命名空间。
  本阶段载荷只是协议快照，不代表通过实体/关系/证据校验；正式编译器必须先做语义校验，
  正式读取仍必须重新验证来源和授权，不能把发布快照当永久可信知识。

隔离测试在既有 CI 的 `karda_p3_test` 数据库内创建随机 schema，完成后只清理该 schema。
测试包含同事件并发、异内容重放、并发 CAS、迟到旧任务、三个修订变化、权限拒绝、
末步注入失败后的完整回滚、重建连接后的重试、不同库隔离及权威更新竞争。
权威竞争通过 PostgreSQL 的实际 Lock 等待状态确认，再提交变更并验证发布拒绝。
本地未配置隔离 PostgreSQL 时明确跳过数据库测试，不能把该跳过算作事务验证通过。

仍待 K1b 后续：生产 DDL/Prisma/210/98 锁步及不可变列授权、完整关系与证据持久化、
真实来源及 OBO 权威适配、同快照读取、失效传播和重建；新库/旧库双迁移演练仍按第 4 节执行。

## 6. K1b-P2：既有表只读适配（原生文本子集）

`read-postgres.ts` 将既有 entity/assertion/evidence/span/document 映射到安全投影，
使用服务角色连接、`REPEATABLE READ READ ONLY` 事务，不增加生产表或修改现有 API。
`readProductAccess` 增加可选事务连接；原调用默认行为不变，新适配在同一快照重用现有角色、
权限与 owner_anchor 校验，无角色、停用或缺少 product.enter/data.read 均拒绝。

范围刻意受限为**同工作空间的 user 所有库**：拥有者或 ws/org 已发布可见，
再与当前用户、工作空间和消费产品的 kb_attachment 相交；请求 kbIds 只能收窄。
尚不覆盖 tenant/platform 所有库、跨工作空间、预设库、Guest 专用读面。
查询先完成权限过滤，再读取实体、断言和原文；不复用旧 300 秒可见集缓存。

平台准入和已发布关系读取器是构造时必需的可信依赖，调用身份必须来自已验证会话/OBO。
目前测试注入准入结果与显式关系，**未接真实平台 OBO 或生产发布表**，也不能把任意候选当已发布知识。
外部准入必须每次权威求值；本地数据库快照不能对外部平台提供分布式原子性。
正式接线仍等待平台撤销契约、来源/关系发布持久化和 K0b 门槛，不能直接把缓存布尔值接入。

发布输入新增冻结的来源清单（库、文档、版本、原始字节 SHA256）。读取时逐项核对
span.document_version、document.active_chunk_version、现行 document.content_hash 及实际对象字节哈希。
仅支持现有原生文本解析路径，复用 `canonicalText/decodeSourceBytes` 的 UTF-16 半开偏移；
并核对 canonical.slice(start,end) 与保存 excerpt 完全相同。
textLength 来自整份同版本规范原文；不从 chunk/excerpt 推算，也不把 PDF 字节解码成文本。
as_of 仍不映射为 validFrom，expires_at 仍独立控制人审失效。

缺少原文、哈希/版本/摘录不符或格式不支持时排除该证据，结果 `sourceStatus=partial`；
该字段只描述已查询候选的原文解析情况，不代表整库知识完整率。
撤回/归档/处理中原文不参与读取，过期或失去最后支持的断言不会形成图谱边。
对象后端异常直接终止，不转成成功空图。候选实体/断言/证据行数各至多 5000，
单文件至多 8 MiB、一次读取累计 32 MiB/100 份，超出累计预算明确失败，避免默默截断证据。

数据库并发语义：本地角色查询建立一致性快照；此后提交的来源撤回或本地角色变更
不改写已开始的快照，但下一次读取必须立即观察到。原文通过冻结哈希绑定该快照；
对象已删除或改写时宁可缺失，不以新字节解释旧锚点。
隔离 PostgreSQL 测试使用现有 41 表及随机库/成员数据，并以 karda_svc 实际执行读取，
覆盖跨空间/私人库排除、取消挂载、来源撤回/版本变化、同版本换字节、摘录错误、
人审过期、类型映射缺失、本地角色撤销、平台拒绝注入、快照竞争与新实例一致性。
这验证产品表的局部适配，不是正式业务数据、真实 OBO、生产权限或 K1b 整批验收。

## 7. K1b-P3：持久发布到读取器的隔离桥接

`release-format.ts` 固定 `karda.semantic.release.v1` 载荷：版本化本体、旧实体 kind 的显式映射、
同库 asserted 关系、支持断言 ID 与冻结来源清单。规范 JSON 边界沿用发布命令的 256 KiB 限制。
拒绝跨库、未知关系类型、非 asserted、重复关系/来源/支持 ID、缺少映射/来源的非空关系集。
结构校验不代替发布时实体/证据/人审权威校验；模型候选不能绕过这些检查。

`publishSemantic` 在开启事务前校验该格式；原通用协议保留用于协议测试。
`PostgresSemanticReleaseLoader` 在 P2 读取器的同一只读快照内联查 head 与 release，
校验库、generation、命令指纹及固定语义定义，拒绝损坏记录或同版本不同定义/映射。
没有 head 的库返回空关系；只查已授权库，历史记录和其他库不能改变当前读面。
多库合并要求本体与映射完全一致，不静默套用一个库的语义解释另一个库。

当前仍只接受随机测试 schema；没有生产 DDL、生产工厂或正式 API。
测试 schema 为服务角色授予 SELECT，写入由隔离测试管理连接执行；这不是生产不可变列授权验收。
测试验证真实发布→数据库持久化→新 loader→既有表证据投影，以及来源撤回后的立即排除，
并验证新旧 head 的一致快照、旧事件重放不回退、损坏指纹拒绝及不兼容语义拒绝。
真实平台准入、来源/人审修订适配及生产迁移仍归 P4/P5，不提前记完成。

## 8. K1b-P4：正式数据层与隔离迁移

增量 `0016_semantic_foundation.sql` 与 baseline、Prisma、98 列授权同步声明 10 张新表，总表数 41→51。
相对第 2 节的 7 个初稿概念，增加独立 `semantic_review`、`semantic_release_source` 和 `semantic_release_review`，
分别保留跨重编译的人审历史、物理来源清单、发布实际引用的人审记录；不增加执行清单项。
本体定义按 kb 绑定，可引用同一 Ontos 版本但不通过共享定义行越库读取。

`semantic_compile_run` 保存已结束的 validated/rejected/failed 不可变快照，含输入/配置/任务指纹、来源清单及候选。
运行中调度沿用任务设施，候选不是发布结果；发布前的状态、候选校验和权威修订比较仍由 P5/K2 事务适配承担。
`semantic_review` 的 subject_key+revision 防止同版本覆盖，保存决策、对象哈希、复核人、理由和修订对象。
这里只保存服务端核验后身份；结构或数据库记录本身不能证明人审身份，不自动导入离线草案回执。

发布版本以 kb+generation 唯一，head 和事件回执复合引用同库、同发布代次。
关系端点、支持断言、来源原件、人审及编译/本体版本通过复合外键禁止跨库绑定。
既有 entity/assertion/document 增加 kb_id+id 唯一索引，原有 UUID 主键保证旧数据可兼容，不回填业务事实。
关系只接受 asserted；类型、证据有效性、来源字节和 canonical text 仍由编译器及读取器检查。

10 表服务角色允许 SELECT/INSERT，不允许 DELETE；除 head 外均不允许 UPDATE。
head 只允许更新 generation/release_id/updated_at；CAS、单调递增和旧事件处理仍由发布事务实施。
97 的通用授权后，0016 和最终 98 均收紧相同权限，重复 db-init 不会恢复审计删除权限。
外键不级联删除发布历史或人审；一旦有语义记录，原件/实体/断言/库的物理删除会被阻止。
用户撤回仍通过现有状态列立即生效，不能为了清理图谱而删除人审。正式接线前需把物理清理变为有保留策略的归档/回收流程。

隔离测试创建随机前缀数据库，在真实 PostgreSQL 上分别执行新库全流程两次、旧 41 表库全流程两次；
核对原有行不变、两种路径列定义一致，并以 karda_svc 实际插入全部新表、验证只读列/删除拒绝、跨库拒绝和重编译后人审保留。
末步注入 FK 失败验证发布和 head 同时回滚，再次 db-init 后核对裁决及权限不变。
代码回退继续读原有表，保留新表及审计数据，不通过破坏性 down migration 撤销上线；生产执行仍须既有 db-init/release 流程。
当前批不接生产路由，也不把表结构交付记为 P5 权威适配或 K0b 业务效果验收。

P4 验证证据：PR290 代码 CI45432097084，992 项测试通过、零失败/跳过；新库与旧 41 表库、全部新表服务角色、跨库约束和回滚测试均实际执行。TypeScript、Prisma validate 和五项护栏通过。生产环境未执行本增量。

## 9. P5 本地建设：正式编译/审核/发布/读取闭环（2026-11-25）

新增 `store-postgres.ts` 使用 P4 的正式 `karda_kb` 表，不再依赖随机协议测试 schema。
服务接受服务端已验证身份和必需的平台准入函数；无环境工厂、生产路由或离线裁决自动导入。
当前覆盖同工作空间、当前用户所有的 user 库；本地权限逐次读取，不以请求中的 roles 代替数据库角色。
写事务使用产品角色编辑器相同的工作空间锁，再取库级语义锁，并持有成员和知识库行锁。
用户角色可写权限和服务发布权限分别控制编译与审核/发布；无角色、只读、停用、外部准入拒绝、库归属不符均拒绝。

- `recordCompile`：规范化冻结候选，验证原件版本、大小、哈希和同版本原生文本；写入固定本体版本及编译快照。
  taskKey 同内容重复返回原 run，不同内容或配置拒绝；同本体版本不同定义或 kind 映射拒绝。
  编译成功只表示结构/输入有效，不代表候选已审核、已发布或业务结论正确。
- `reviewRelation`：每条关系以稳定关系 ID 为 subject_key，CAS 比较人审 revision，追加 accept/revise/reject。
  subject_hash 绑定关系、语义定义及来源清单，复核人取已验证调用身份。重编译不删除、重写或批量认可裁决。
- `plan`：创建绑定 compileRunId、来源/本体/人审修订、预期 head generation 和事件 ID 的不可变发布计划。
  所有关系必须有与当前候选匹配的最新 accept；分析与提交分开。
- `publish`：重新授权并核对计划、最新人审、来源字节、实体类型、断言当前状态/人审过期、支持片段与原文。
  完整复用安全图投影的关系可用性判定；建议关系、失效证据、换字节/版本、过期断言不允许发布。
  正式 release、关系、支持、来源、人审绑定、head 和事件回执同事务写入；同事件同指纹重放只回历史回执，异内容拒绝。
  新事件通过 generation CAS 推进；重放不恢复旧 head，也不提供现行读取授权。
- `PostgresFormalSemanticLoader`：在现有读取器已授权的同一只读快照中读取当前 head，校验发布指纹、编译/定义绑定、
  规范化关系/支持/来源/人审记录与快照一致；损坏或不兼容语义显式失败，不返回成功空图掩盖错误。
  新裁决使旧发布对应关系在下一读取快照失效；即使再次 accept，也须新发布绑定该裁决后才恢复。
  最终来源撤回、版本、字节/偏移和权限过滤仍由现有 `PostgresSemanticReader` 完成；新实例无需本地缓存恢复。

`semanticValueHash` 复用有界规范 JSON，固定 envelope 作为值指纹域；不依赖 JSONB 键顺序。
发布持有来源/实体/断言行锁。evidence/span 的运行时 UPDATE 权限保持为零，因此不用需要 UPDATE 授权的行锁，
而使用 SHARE 表锁阻止支持证据并发写入/删除直到提交。它不阻塞普通读取，但会扩大发布与既有加工写入之间的竞争；
在开放正式接口前需按真实负载评估，后续若细化锁必须覆盖所有写入路径，不能通过开放不可变列 UPDATE 来绕过。
外部平台准入和本地事务没有分布式原子性；注入准入测试不是正式 OBO、席位通知、tenant/platform 或预设库的真实联调。
P5 的完整权威适配仍未完成；本批先交付可供 K2 使用的本地正式表闭环。

## 10. K2a 本地关系候选编译（2026-11-25）

新增 `compiler.ts`，复用既有 `GenerationClient`、`extractSelection()` 与 Atlas 错误映射。
`AtlasSemanticCandidateClient` 走产品抽取端点，不另设模型供应商或凭据；模型输出上限 4096 token，
响应最多 64 KiB/200 条候选。只接受 relations 信封和明确字段，资料始终放在 user 数据消息，
系统指令明确禁止执行来源指令、工具调用、发明实体/证据/人审。无端点授权仍按现有能力等待错误返回，不假造结果。

正式 `loadCompilerSnapshot` 在读取任何来源及模型外发前检查平台准入、当前 data.write/ai.use 与 user 库归属；
校验最多 100 份同版本原生文本、32 MiB 累计字节，复用原件哈希和 UTF-16 片段一致性检查。
只加载当前 indexed/verified、未替代、未过期且有同库同版本直接支持片段的断言；不把文档 verified 传递给断言。
输入快照最多 1000 实体、200 断言、每断言 16 片段、规范 JSON 256 KiB，超预算明确失败，不默默截断。
调用者提供的本体固定版本和 kind 映射仍是受信任服务配置，不是 HTTP 请求中的任意对象。

确定性编译器仅在当前库内按类型及规范化名称/别名解析现有实体；NFKC 和空白规范化，不做模糊猜测或跨库并名。
名称歧义、缺失实体、类型不符、未知支持断言、非法字段、重复关系分别给出拒绝原因。
稳定关系 ID 由库/固定本体/类型/端点生成，不随模型排序或重跑随机改变，支持后续人审跨编译保留。
同一来源端点和类型的不同目标列为待审核替代项；当前本体未定义函数性，因此仅作为冲突提示，不声称逻辑互斥。

`runSemanticCompile` 冻结已授权快照，在数据库事务外调用模型，然后进行确定性校验。
出现拒绝/替代项时返回诊断，不将部分/空筛选结果误存为清空知识的编译；合法结果调用正式 `recordCompile` 再次检查权限及来源。
任务键绑定 taskId、输入快照、编译器/提示词版本与模型选择配置；无审核或发布调用路径。
候选载荷沿用未来发布格式的 asserted 字段，但只是未发布快照，必须经逐关系人审和原子发布后才进入现行知识读面。
模型推断的支持关系仍需业务人员判断；指纹、UUID 或来源片段存在不代表结论正确。

隔离 PostgreSQL 验证正式输入加载→模拟 Atlas generation 协议→实体/关系编译→正式快照入库，
确认现行图仍为空；验证只读角色拒绝、到期断言不外发、撤回原件拒绝。

不把注入 generation 当真实 Atlas 联调，不关闭 K2a 或 P5。
