# Karda 产品运营成员、多人 Owner 与角色授权设计

日期：2026-11-28；2026-11-29按飞书正文核对修订。状态：产品侧设计，待批准实施。适用：Karda workforce 产品运营面，不改 customer 租户角色。设计依据：用户本轮确认的三点，以及[平台方案](https://vxturestudio.feishu.cn/wiki/HBBQwpTRSibuH3km3sOc0QkEnzb)。2026-11-29已通过用户打开的内置浏览器读取设计v0.2、接口目录API-INDEX v0.1及API-OPS-001 v0.2-draft中的通用约定、OPS-07/08、事件与计量章节。平台正在设计实现，所有线上端点、事件名、签名和字段以正式交付契约为准。

## 1. 产品定位与责任划分

accounts负责workforce身份认证；平台负责“哪些人被关联到Karda，以及其中哪些人是owner”；Karda负责“非owner成员可执行哪些产品操作”。admin/opera/arche权限与Karda资格无继承关系。平台member是产品关联身份，不是Karda业务角色，更不是customer租户的member。

| 事项 | 权威方 | Karda行为 |
| --- | --- | --- |
| workforce账号、认证、停用和会话 | accounts/平台 | 复用独立RP，不创建账户或密码 |
| Karda产品成员资格、owner/member关系，支持多个owner | 平台 | 接收和核验当前关联，不允许本地新增/删除平台成员或提拔owner |
| 产品权限目录与业务角色 | Karda | 定义权限、内置角色、自定义角色、角色版本及范围 |
| member的业务角色分配 | Karda | 仅向当前有效平台成员授予；仅当前平台owner可管理，member不能授权 |
| 公共知识资产与业务状态 | Karda | 产品所有，员工离职或owner变更不改所有权 |

这里的owner是平台关联到本产品的受保护授权身份，Karda实现其受保护的运营人员与角色授权管理能力。不是员工身份域的新角色，不是某租户工作空间的owner，也不是可以读取客户私有数据的全站超级管理员。

## 2. 两层模型

第一层为平台产品关联：product_code=karda、workforce主体、association_kind=owner/member、当前有效状态与权威版本（均为语义占位，非既定wire字段）。一个产品可有多个owner，每个owner独立生效；移除其中一人不会影响其他owner。没有owner时Karda进入“等待平台分配owner”，不通过本地口令自建owner。

第二层为Karda业务角色：一个member可以有多个角色，取有效权限并集，受资源范围、业务约束和平台当前资格限制。新member获准进入运营面的个人准入说明页，默认没有内容读取/编辑/发布权限，只能看到本人关联和“尚未分配业务角色”的说明。平台是member不等于普通知识编辑员；角色名称member不再用于运营侧业务角色。

owner是一条受保护系统授权路径，不生成一个可编辑的本地owner角色。owner自动拥有本产品成员与角色授权管理权限；内容编辑、审核、发布等业务权限另行显式分配本地角色，不自动全开；其资格只能由平台变更。前台在成员列表中标记“Owner · 平台管理”，不提供授予、转让、撤销owner按钮。本地无法停用owner资格；需撤销时由平台办理，Karda收到当前权威后执行。

## 3. 权限计算与业务约束

授权条件 = 有效workforce会话 ∧ 当前有效Karda平台关联 ∧ （owner具备所需授权管理权限，或当前业务角色包含所需内容权限及资源范围）∧ 操作自身约束。

- owner自动获得产品授权管理能力，内容业务权限单独求值，平台无关联、关联撤销或账号停用时均无权；本地历史角色不能恢复资格。
- member角色不得产生owner/平台成员资格。未知权限码、角色停用、角色删除或范围不匹配均不放行。
- 所有owner仍受原文证据、版本CAS、时效、独立审核、禁止客户私有数据越权等约束。“有权限审核”不代表可以审核自己编辑的内容。
- 高风险授权/发布/撤回操作明确影响预览、操作原因、确认和审计；不假定普通登录就满足平台未来的step-up要求。
- 产品范围是Karda公共运营资产；customer的订阅、workspace角色、私有库权限保持原授权体系，不与workforce角色合并。

## 4. 产品权限与内置角色

角色权限取受控代码目录，不支持用户输入代码表达式、SQL、任意API路径或自定义可执行策略。新增代码由Karda软件版本提供；角色编辑只选择已有权限。

| 权限组 | 主要能力 |
| --- | --- |
| 运营入口/读取 | operations.enter、content.read |
| 公共库与分类 | library.manage、taxonomy.manage |
| 来源与加工 | source.manage、production.manage |
| 知识与关系 | content.edit、graph.manage |
| 审核 | content.review |
| 发布 | content.publish，覆盖发布/撤回/版本恢复/发布图索引变更 |
| 审计与导出 | audit.read、content.export |
| 授权管理 | members.manage、roles.manage（仅平台owner持有，member不得通过自定义角色取得） |

实施时对齐当前content.edit等历史权限，不凭拆分码遗漏既有路由。每个路由、后台动作和导出都登记对应权限与范围。

| 内置角色 | 用途 | 默认范围 |
| --- | --- | --- |
| 公共库管理员 | 库设置、分类、来源和加工组织；不自动审核/发布 | 产品级或指定库 |
| 知识编辑 | 来源/条目/关系编辑、加工候选 | 指定库或产品级 |
| 知识审核 | 独立内容审核 | 指定库或产品级 |
| 发布经理 | 发布、撤回、回退和发布索引 | 指定库或产品级 |
| 运营审计员 | 查看必要操作历史，不改内容或权限 | 产品级 |
| 只读成员 | 已获授权公共内容读取；导出需单独授予 | 指定库或产品级 |

支持owner创建自定义业务角色：名称、说明、权限集、状态、可授权范围、版本。系统角色定义只读，可通过复制创建自定义角色。角色停用即失效；删除采用归档并保留审计，不删除历史授权。

members.manage和roles.manage为受保护owner管理权限，不能加入member的内置/自定义业务角色，也不允许将授权职责委派给member。owner可给自己或其他有效人员分配业务角色并留下审计；分配给自己的内容权限仍受独立审核约束。平台准入变更若在产品前台提供操作，必须使用平台正式交付的受约束写入协议，实际事实写回平台；当前API草案仅给出Opera管理面写入，不转发Opera Cookie，不自行发明产品写接口。

## 5. 操作范围与页面

资源范围首期只支持“全部产品公共库”和“明确指定库列表”。同一条授权包含角色和范围；角色有权限但范围不含该库仍拒绝。产品级成员/角色管理不能通过库范围获得。尚未分类的新库不会因旧的指定库授权自动进入范围。

角色跨库权限不自动扩张：查询、图谱、原件、导出和生产计划逐库检查。跨库关系必须分别有权，响应过滤不能泄漏不可读节点/来源。当前全产品授权迁移为显式产品范围，不猜测现有库级配置。

前台设置→产品成员：列表展示姓名/主体、owner/member平台身份、关联状态、来源版本、产品业务角色、范围；只从已同步的有效成员中选择授权对象，不再手填任意opr_创建本地成员。平台关联操作显示来源说明和入口链接（链接以平台正式交付为准）。显示全部owner，不设唯一owner锁或本地转让按钮。

前台设置→角色与权限：内置/自定义角色、权限分组、范围、被授权人数、变更影响预览、启停与历史。成员授权支持多角色、明确库范围、变更前后对比、原因、CAS及幂等。

前台设置→接入状态：成员快照版本、最近成功核验、消息/对账状态、失败原因和恢复入口；不展示密钥、原始令牌或后台委托密文。角色不足、无平台关联、会话失效、平台暂不可核验分别提示。

## 6. 平台成员接入：产品侧适配要求

在Karda建立唯一适配器，输出平台产品关联的标准化当前视图。优先复用正式交付接口/SDK；本文不新建平台规范，不假定token claims、C2或既有租户provisioning可以承载workforce产品关联。以下是消费方需求，不是既定API：

- 可验证当前主体对karda的owner/member资格，并读取授权管理所需成员目录和状态，支持分页、版本与一致快照。
- 消息只是失效/变更提示；校验受众、签名、事件ID、顺序、版本和环境，拒绝重复/乱序覆盖；遗漏后通过正式当前快照对账。
- 完整快照成功后才根据缺席撤销成员；半页失败不当作人员移除；平台已确认撤销须立即压过本地角色和缓存。
- 平台返回不可核验时，管理、授权、发布及后台写入拒绝；读取的有效期与降级边界以正式契约确定，不自行发明24小时有效期。后台不得以本地镜像代替当前授权。
- owner/member为平台权威事实；JWT中历史owner标志不成为永久本地管理员。具体核验频率、快照租约和事件延迟按正式契约冻结。

## 7. 数据设计（Karda本地，仅逻辑设计）

| 逻辑表 | 内容与边界 |
| --- | --- |
| product_operator_membership | product/subject、owner/member、有效状态、平台记录/权威版本、同步批次；只供平台适配器写入 |
| product_operator_sync | 快照版本、分页进度、成功核验、对账状态、重试；不存账户密码 |
| product_role | 稳定ID/代码、名称、系统或自定义、状态、当前版本 |
| product_role_version | 不可变权限集合、名称/说明、操作者和变更原因 |
| product_member_role | 平台成员引用、角色引用、product/library范围、状态与修订 |
| product_authority_revision / event receipt | 授权修订、幂等收据与乱序/重投处理；尽可能复用既有审计/版本基础 |

最终表数、DDL增量和字段在实施时按现有数据规范冻结；不改workforce账户表，不把平台数据复制成新的身份中心。ops_audit继续承载审计；资格变动、角色分配、范围变化、角色版本变更分别留痕。平台成员撤销后本地分配保留为历史/失效，重新关联默认不自动激活旧授权，需owner确认；owner资格只按新平台事实恢复。

## 8. 后台加工与授权撤销

现有加密、有限期会话委托继续用于表达员工发起任务，不替代平台关联。执行和落库前必须检查会话、当前平台成员资格、当前角色/owner、任务与库范围、源版本、任务修订；任何版本变化触发重新核验，拒绝旧在途结果。

降为member的owner只保留另行有效的本地业务角色，未配置则无内容权限。移除平台关联、撤掉角色/范围、停用角色时相应任务暂停；已完成内容保留产品所有权，不回滚审计和发布历史。任务重试和恢复需重新授权，不能用旧owner事实补回权限。

Jena建索引、发布、恢复、查询和导出使用同一产品授权适配，不再依赖固定OPS_ROLES枚举；后台写入不刷新用户会话，不消费客户权益。

## 9. 现有版本差异与迁移

当前基线v0.12.60／bfda1925，ops_member.roles使用固定枚举，没有平台关联权威，也没有owner和自定义角色。首任授权通过本地一次性口令，前台允许手填opr_授权。以下旧设计被本方案替代，尚未实施：

1. 停止本地bootstrap作为正式授权源，移除路由、表单和KARDA_OPS_BOOTSTRAP_*配置说明；不设置“平台出错时恢复bootstrap”的后门。
2. 平台分配的多位owner直接获得本产品owner能力，不需要第二次口令、不依赖已有ops_member行。平台没有owner时等待分配。
3. 固定OPS_ROLES变为内置角色目录＋持久自定义角色。旧authorization不得迁成owner或拥有授权能力的member；保留历史，产品管理能力仅来自平台owner。
4. 先读取真实既有授权清单和平台关联，再迁移匹配成员的业务角色；不假设生产为空。现有未匹配、停用或已撤销成员的角色保留历史，不能放行。
5. 接入新平台契约并完成一致快照前，新运营授权路径保持关闭；没有平台登记的账号不会因旧角色保留进入权限。禁止新旧守卫任一通过即放行。
6. public_library/artifact/release/job和原件不换所有者；member/owner变化只改变操作权限。
7. DDL追加、保留历史和审计；回退应用如会恢复本地bootstrap/旧授权路径，必须同时关闭运营入口与后台任务，不能回滚成可绕过平台资格的旧版本。

## 10. 端到端验收

- 两名及以上owner分别登录并完整管理；撤一人另一人保留，不能从Karda产生owner。
- 平台新增member无默认内容权限；owner分配内置/自定义多角色和库范围后按实际权限进入。
- owner降级member、平台成员移除、账号停用、会话撤销即时进入正确拒绝/降级路径；已缓存角色和委托任务不能复活资格。
- 自定义角色修改/停用、授权范围收缩、委派管理员自提权/越界分配、错误产品/realm/audience、跨租户内容均正确拒绝。
- owner审核自己编辑的内容仍被拒；独立审核、发布指纹、回退、失效证据约束保持有效。
- 平台分页不完整、重复/乱序事件、并发授权、快照失效和临时不可用可恢复，不扩大权限。
- 后台进行中撤权/改角色/移除库范围，结果无法提交；恢复需新授权。
- 原customer工作台和租户角色保持独立，公共资产归属不变。

## 11. 决策与实施顺序

建议下一完整板块为“平台产品成员接入与Karda角色授权中心”，O1–O6＋R1/R2：契约适配、多owner、角色目录与自定义、成员授权与范围、统一权限贯通和后台围栏、迁移运营与审计。完整计划见[214](../70-workplan/214-product-members-owner-role-plan-20261128.md)。本轮仅设计，未变更生产角色、接口或认证配置。模型/OCR费用仍按平台758独立对接，不与owner/member机制混为同一能力。

## 12. 2026-11-29飞书正文核对结果（覆盖此前相反表述）

已读取[设计v0.2](https://vxturestudio.feishu.cn/wiki/HBBQwpTRSibuH3km3sOc0QkEnzb)、[接口目录](https://vxturestudio.feishu.cn/wiki/BMqTwyzRbilVphkYuotc7RE0nwd)、[API-OPS-001 v0.2-draft](https://vxturestudio.feishu.cn/wiki/H1SswJnHyitBhgk6egVcV0Rxngc)相关章节。页面明确P1–P4未实施，接口全部候选、不可直接调用；本记录不是生产实现证明。

1. owner是产品运营授权管理员，非资产所有人/付款人；建议两名，启用至少一名。Karda将授权管理与内容业务角色分离，不默认把owner的编辑/审核/发布全开。这是产品侧最小权限设计，平台未要求owner拥有全部内容权限。
2. member不能授权；删除本方案先前允许member成为授权管理员或受限委派的设计。owner已包含准入，不另建重复member关系。
3. 人员准入/owner任免可以在产品前台提供入口，但写回平台权威。当前草案OPS-01–06属于管理面，采用Opera本人会话；产品不得获得Opera Cookie。正式产品面写契约未交付前只提供平台入口说明，不直连这些管理写API。
4. 候选OPS-07 GET /platform/operations/access无业务参数，从可信登记/员工委托解析product/subject/environment。authorized=false是200且role=null；401/503分别保留认证失败/权威不可用，不能转成普通无权。authorization_version使用十进制字符串，不视为授权本身。
5. 候选OPS-08 GET /platform/operations/members要求当前员工为owner，单独服务凭据不够。分页必须同authorization_version完成，版本冲突重读；不设计独立后台服务账号无owner委托拉全量员工目录。普通member只核验本人准入。
6. 事件名/路径/签名/恢复协议未冻结，只定义失效后重新求值；不能猜造事件。请求、空闲页面、后台步骤分别取证；外部在途调用只能尽力取消。
7. 平台负责最后owner原子交接和突然离职后Opera补任；Karda提示单owner连续性风险、无owner待补任，不本地生成继任者或回退superadmin。
8. 沿用已有能力权益；运营用途产品归集与客户扣额隔离。owner身份不授予费用权限。MTR-01/02/03/04及COST-01路径/鉴权仍待定；缺价格或回执显示待核算，非零费用。模型/OCR仍不调用。

仍待冻结：真实员工委托票据、正式基址、产品人员准入写入通道、跨环境授权范围、owner互相任免限制、权限失效时效、后台接管与计量/预算协议。本轮只修订本仓设计文档，不修改飞书、平台issue、代码或生产授权。
