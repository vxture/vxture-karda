# 140 - 断言模型:Fact / Claim / Entity / Evidence

Status: v0.2(2026-08-26)。§11 的第 1、3 条已落槌(**KD-209** / **KD-210**),schema 可以落地;其余三条待拍板,不阻塞本轮实现。实现属批次 15。

定位权威 `20-specs/30-agent-knowledge-blueprint.md`(KD-017);本文是它在对象模型
层的落地,与 `100-kb-model.md`(v1 模型)是**增量关系**,不推翻其中任何一条。

## 1. 为什么是现在

KD-017 把定位提升为「Vxture 面向 AI Agent 的共享知识基础设施」,并给了两条硬约束:

> **RAG 是机制不是边界,Chunk 是中间产物不是核心模型。**

v1 的核心对象是 KnowledgeBase → {Document → Chunk, Entry}。这是一套**载体模型**:
它回答「这份内容在哪、怎么切、怎么召回」,不回答「它**说了什么**」。对一个把知识
供给给 Agent 的平台,后者才是产品。

三条独立的线同时指向同一个缺口:

| 线 | 事实 |
|---|---|
| **产品自己的画布** | 加工管线的五阶段是 `理解 → 萃取 → 编织 → 验证 → 入藏`,管家提案里有「冲突裁决」(两份文档对同一件事说法不一致)。**UI 早就假设了断言层存在**,只有模型没跟上 |
| **下游** | yucer 把「据谁所说、何时、哪一版」列为外部知识进入其判断路径的硬条件(`#103` Q14)。行级溯源已完备,断言级是他们最终需要的 |
| **登记册** | 批次 15 是登记册里最大的一处设计-实现落差 |

---

## 2. 缺口的准确形状

v1 能回答的:

- 这段文字来自 `document#42` 的第 3 块 → **行级溯源**,已完备;
- 这份文档由谁上传、何时索引、验证状态如何 → **文档级治理**,已完备。

v1 **不能**回答的,而 Agent 每一次引用都需要:

1. 「单架次时长 25 分钟」这句话本身是什么对象?今天它只是 chunk 里的一段字节,
   没有 id,不能被引用、被验证、被推翻;
2. 这句话**是谁说的**——不是「谁上传了文件」,是文件里那个作出断言的主体
   (《作业手册 2026》的编制单位),以及**截至什么时候**成立;
3. 两份文档就同一件事给出不同数字时,系统凭什么知道它们在**谈同一件事**?

第 3 条是关键:冲突检测不是文本相似度问题,是**同一断言的两个版本**问题。没有
断言对象,「冲突裁决」这个已经画在管家提案里的功能没有可实现的定义。

## 3. 对象模型 v2

新增三个一等对象。Document / Entry / Chunk **不变**,Chunk 的地位按 KD-017 下调
为检索机制的中间产物。

```
KnowledgeBase
  ├── Folder
  ├── Document ──── Chunk ─────────► 检索机制(向量/词法)
  │      │                              ▲
  │      └── Span ◄──┐                  │ v1 检索单元,不变
  │                  │                  │
  ├── Entry ─────────┼──────────────────┘
  │                  │
  ├── Assertion ─────┘  Evidence:断言 → 它的依据(某个 Span,或另一条 Assertion)
  │      │
  │      └── AssertionMention ──► Entity
  │
  └── Entity(库内业务对象注册表)
```

### 3.1 Assertion —— 一条有溯源的陈述

蓝图列了 Fact / Claim / Event / Procedure / Rule 五种。它们**不是五张表**,是一张
表上的 `kind` 枚举:五者的字段需求一致(主语、陈述、时效、来源、置信),差别在语义
而非结构,分表会立刻带来五份重复的溯源与治理逻辑。

| kind | 是什么 | 例 |
|---|---|---|
| `fact` | 可核验的客观陈述 | 项目预算 = 380 万元 |
| `claim` | 来源作出的判断/结论 | 该方案在雨天不具备作业条件 |
| `event` | 带时间的发生 | 2026-03-14 完成验收 |
| `procedure` | 有序步骤 | 断路挂牌五步 |
| `rule` | 约束/规定 | 风速 > 10 m/s 禁飞 |

### 3.2 Evidence —— 断言与其依据之间的边

不是断言的一个字段,是**一条边**,因为一条断言可以有多个依据,一个依据可以支撑多
条断言,而且依据可以是**另一条断言**(推导链)。做成字段会在第一次遇到「两份文档
都支持这条」时就崩掉。

### 3.3 Entity 与 AssertionMention

Entity 是库内业务对象的注册表(「XX应急管理局」「XX无人机项目」)。断言通过
`AssertionMention` 提及实体——同样是边,同样因为多对多。

**Entity 不做跨库合并**:同名实体在两个库里是两个 Entity。跨库消歧是本体问题,
属 Ontos 平面(五平面分工:Atlas 想、Runos 做、Karda 知、Arda 存、Ontos 定义语义),
不属 karda。这条边界现在写下来,免得实体表长成一个半吊子本体库。

## 4. 断言级溯源:yucer 那三个问题

| 问题 | 承载 | 说明 |
|---|---|---|
| **据谁所说** | `assertion.asserted_by` | **不是**上传者,不是抽取模型。是来源中作出该断言的主体 |
| **何时** | `assertion.as_of` | 该断言的时效起点;`valid_until` 可空,表示未声明失效 |
| **哪一版** | `evidence.document_version` | 依据所在文档的版本;文档重建后旧版本的 evidence 仍可解析 |

三者必须**同时**回答,才算断言级溯源。只给出「来自 document#42」是行级,yucer 明确
说过那不够。

**抽取者与断言者是两回事**,必须分开落列,这是本节唯一容易做错的地方:

- `asserted_by` = 《作业手册 2026》的编制单位 —— **内容的权威**;
- `extracted_by` = 做抽取的模型/管家运行 —— **过程的责任**。

把两者混成一列,产品就会告诉 Agent「这句话是 karda 说的」。那是最坏的一种错误:
它把来源的权威悄悄换成了我们自己的。

## 5. 与检索的关系:本轮**只做溯源层**(owner 2026-08-26)

两条路都成立,本轮取前者:

| | 本轮采纳 | 登记为下一步 |
|---|---|---|
| | **溯源层** | **检索单元** |
| 检索走什么 | 仍是 chunk / entry,零改动 | 答案变断言形状,chunk 退为兜底 |
| 断言的作用 | 挂在结果上,供引用、溯源、冲突检测 | 直接被召回与排序 |
| yucer 的依赖 | 满足 | 满足 |
| 风险 | 无检索回归 | 需重做排序,且当前评测基线不覆盖 |

理由:yucer 的依赖是**溯源**不是检索;而检索是目前唯一跑通、且被评测集覆盖的链路,
不该在断言模型尚未经真实语料验证时先动它。断言层先跑起来、被验证过、冲突检测有
实际产出之后,再谈让它承担召回。

**这不是把难题往后推**——溯源层本身就要求抽取管线、实体注册、冲突检测全部落地,
那是批次 15 的主体工作量。推后的只有排序。

### 5.1 置信与排序(KD-210)

`confidence` 是抽取时的机器置信。**人确认前参与排序,确认后不参与**:

- **未确认**的断言,置信是它唯一可用的质量信号,不用它就只能按时间或随机;
- **已确认**的断言,`verified` 是更强的信号。此时再让机器置信参与,等于让人的判断
  被模型分数稀释——一条人确认过的断言不该因为模型当初没把握而排在后面。

因此 `confidence` 在 `verification_state = 'verified'` 之后**不参与打分**,但**不清空**:
它是抽取过程的记录,清掉就没法回头评估抽取器的质量。

## 6. 与治理的关系

断言**复用**既有的 `verification_state` 三态机(`unverified` / `verified` / `stale`),
不发明第四套状态。理由:验证治理的定义是「人确认过这条内容可信」,对断言的适用性
比对文档更强——文档是一个容器,断言才是可被确认或推翻的最小单位。

由此带来一处必须现在想清楚的**口径问题**:

> 一份文档已验证,从它抽取出的断言是否自动继承 `verified`?

**可参考,不继承(KD-209)。** 继承会让「验证」这个词失去意义:人验证的是文档,不是
模型从中抽出的每一句话——抽取本身可能出错,而这正是验证要拦的东西。断言默认
`unverified`,经管家预验后进「待你确认」,人确认才是 `verified`。

**「可参考」是这条裁定里带工程后果的那一半**:来源文档的验证状态是一个可被读取的
**信号**,不是一个可被复制的**状态**。它的两个用法:

- 管家预验时据以提高置信——出自已验证文档的断言,预验通过的门槛可以低一些;
- 检索排序时据以加权(与 KD-210 的置信一并,见 §5)。

工程上的落法很关键:**不落一列 `source_verified`。** 那会立刻变成一份需要跟着源
文档变化而同步的快照,也就是一份会过期的副本。信号在读取时沿 `evidence → span →
document` 取,永远是当下的真值。

这与 KD-208(覆盖率分母不排除未开治理的库)一致:分母只会变大,覆盖率会因为断言
的引入而**下降**,那是真实情况——那些断言确实没被验证过。**不为了让数字好看而改
口径**,这条已有裁定,此处只是它的延伸。

## 7. 与 KD-206(全域回收)的关系

KD-206 裁定客户删除请求触发**全域回收**。断言引入后,回收必须穿透到断言层。

**外键能表达的部分**(已在 dev 库实测,见 §9.1):

| 删除 | 结果 |
|---|---|
| KnowledgeBase | 其下 Assertion / Entity 全部级联删除 |
| Document | 其 Span 级联删除,挂在这些 Span 上的 Evidence 一并级联 |

**外键不能表达的部分,也是本节的要点。** 实测确认:删除一份 Document 之后,
`span = 0`、`evidence = 0`,而 **`assertion = 1` —— 断言还在,只是没有依据了。**

这不是缺陷,是正确的:一条断言可以同时有两份文档作依据,删掉其中一份不该连坐。
外键管的是**一条边**,而「它失去了**最后一条**边」是个两跳条件,FK 表达不了。

由此产生两件必须做的事,**分属读写两侧**:

1. **读侧不变式**:**没有依据的断言不可召回。** 这不是一项清理任务,是定义——它没有
   依据,而有据回答是这个产品的前提。读路径按 `EXISTS(evidence WHERE stance =
   'supports')` 过滤,不依赖任何清理作业是否跑过;

   **注意是 `supports` 而不是任意 evidence。** 裁决落败的断言会留下一条
   `contradicts` 边指向胜者,而那条边指向的是**另一条断言**、不是 span——所以文档
   删除的级联带不走它。若按「有没有 evidence」判断,落败方会被它**记录自己落败的那
   条边**证明为「有依据」。这一条是实测抓到的(见 §9.2),不是推演出来的;
2. **写侧回收**:KD-206 是**删除请求**,行必须真的消失。文档删除后需要一次扫描,把
   失去全部依据的断言转为 `deleted`。形态与既有的续验扫描一致(`sweep`),可复用。

先做第 1 条:它是安全属性,即使扫描从没跑过也成立;第 2 条是合规动作,可以异步。
**反过来做是错的**——只有清理没有过滤,意味着在扫描跑完之前,无依据的断言仍在被引用。

Entity 若失去全部提及,**不自动删除**——实体注册表是库级资产,可能被后续内容重新
提及。留空实体不构成数据残留(它不含来源内容)。

登记册里 KD-206 的未答子问题(回收是否穿透副本)在断言层有同样的形态,**一并在
§11 提请裁定**。

## 8. Knowledge API 扩面

关键发现:**现有引用 id 已经是把手**。`karda.ask` 返回的 `citations: [{ id, kbId }]`
中的 `id` 就是检索单元 id,新工具拿它往上走即可,**现有契约零改动**。

| 工具 | 入参 | 出参 | 依赖 |
|---|---|---|---|
| `karda.get_evidence` | 引用 id | 该引用支撑的断言 + 每条断言的 `asserted_by` / `as_of` / 文档版本 | Assertion + Evidence |
| `karda.find_entity` | 实体名/别名 + 范围 | 匹配的 Entity + 提及它的断言 | Entity + Mention |
| `karda.get_context` | 引用 id | 该引用在原文中的上下文跨度 | Span(不依赖断言,可先行) |
| `karda.browse` | 库 + target + 游标 | 库内断言/实体的分页浏览 | 全部(§8.5) |
| `karda.retrieve` | —— | 检索单元化之后才有意义 | **不在本轮** |

`get_context` 只依赖 Span,不依赖断言层,**可以先行交付**——它是四个工具里最便宜
且立刻有用的一个。

每件工具的**调用方式与实现状态**登记在 `260-external-interfaces`——含一处本节看不出的
事实:断言层这两件工具目前**只在直连通道上**,Runos 面仍是五件。

### 8.1 `find_entity` 的四条判断(已交付)

工具面从九件增至十件。形状之外,有四处是**判断题**,不是实现细节:

1. **精确命中直接压掉部分命中**,不是排在前面。混排等于把「该信任我们哪一条匹配」
   推给调用方,而那是我们的活。名或别名任一精确即算精确,大小写不敏感。
2. **擦边一定报 `partial`**。问「应急管理局」拿到「XX应急管理局」,调用方必须知道
   注册表里没有它问的那个——擦边被读成确认,是知识工具最坏的错法。
3. **断言按 `as_of` 倒序**,无日期垫底。问题是「关于它我们知道什么」,天然轴是时间;
   按验证状态排会把一条新鲜的未验证事实压在陈旧的已验证之下,对要据此行动的 agent
   恰好是反的。
4. **计量按次收**,与 `get_evidence` 不同。区别在这一次调用**是什么**:`get_evidence`
   是复核调用方已经付过费的那个答案,给复核标价等于给核验设门槛;`find_entity` 是
   对语料的一次新提问,和检索同类,同样计价。

被裁决落败的断言**照样返回并标注** `superseded_by`——「我们曾认为 X,现在认为 Y」
本身是信息;藏起来只会让 agent 从更旧的引用里重新推出旧值,却永远学不到它已被取代。

### 8.3 `get_context` 的三条判断(已交付)

1. **不用相邻 chunk 拼上下文,读原文。** 最省事的实现是返回 chunk n-1/n/n+1:
   一次查询,不碰对象存储。但 `chunk.ts` 自己写着 chunk text「**不是** canonical
   文本的切片——前缀是合成的,元素内容是归一化过的」。拿它当上下文,等于**用我们的
   检索索引回答「原文是什么」**。KD-017 早已定过这件事的一般形式:chunk 是中间产物,
   不是核心模型。
2. **锚点不由调用方选,只能选宽度。** 调用方给 `radius`,位置永远是那条引用。
   这一条限制才是「免计量」能成立的原因:未计量的总触达 = 手上引用数 × 2×上限,
   而引用只能来自 `search` / `ask`——那两件是计费的。**把宽度换成任意偏移,这就变成
   一个不计费的整篇读取接口。**
3. **对不上就拒绝,不做尽力而为的切片。** 版本换了(`stale_version`)、区间超出
   当前文本(`source_mismatch`)、字节不是文本(`not_text`)一律不返回窗口。切出一段
   短的,看着像真段落而其实是任意一段——这比报错坏得多。

窗口边缘**向外吸附到行边界**,吸附额度是 radius/4。按行不按词是判断:中文没有空格,
按词吸附会在英文上生效、在这个平台真正服务的语料上悄悄什么都不做。额度封顶是为了
一篇没有换行的文档不能把有界窗口撑成整篇读取。

### 8.5 `browse` 的四条判断(已交付)

**为什么需要它。** 另外五件读工具都从调用方**已经有的东西**出发:一个查询、一条引用、
一个实体名。browse 只从一个库 id 出发——这正是它的用处。一个 agent 要判断**该不该关联
这个库**,靠检索是判断不出来的:查不到东西,可能是库不相关,也可能是它猜错了词,
**这两种情况从外面看一模一样**。

| | 判断 | 理由 |
|---|---|---|
| 列什么 | **断言与实体**,不是文档 | 文档是我们**摄入**的,断言是我们声称**知道**的,只有后者可核 |
| 分页 | **keyset 游标**,不是 offset | 这个语料是边写边读的:`OFFSET 25` 下,第一页与第二页之间每插入一行,就有一条没看过的行被挤过边界,**调用方永远看不到它,也没有任何东西报告它被跳过** |
| 游标取自 | **最后一条取到的行,不是最后一条留下的行** | 过滤会丢掉窗口里的任意行;若游标指向最后一条幸存者,它之后被丢掉的行会在下一页被**再取一次、再丢一次**,一个尾部全是草稿的库将**永远翻不到头** |
| 能看到什么 | 与检索**同一条** recallable 规则 | browse 是最容易被说服开例外的那一件(「它是给审计用的,全都给看」)。那个说法在这个面上是错的:审计草稿的地方是 Console——有会话、有身份。一个替检索所拒之物开门的 agent 工具,叫什么名字都是后门 |

**一条要说清而不是让人撞见的后果**:抽取产出的断言落 `draft`,所以**一个刚跑完抽取的库
browse 出来是空的**,直到裁决把它们提上去。这是对的——什么都还没确认——但它意味着
**空页不等于空库**。

### 8.2 端到端实测:两个只有真库能抓到的缺陷(2026-08-26,一次性库)

十项探针全绿之前,抓到两处单测**结构上不可能发现**的问题:

- **别名匹配是死的。** 排序层的别名规则只能对「查询已经返回的行」生效,而 SQL 过滤
  只匹配 `name`——只靠别名能找到的实体根本到不了排序层。单测把行直接喂给排序函数,
  于是十一条全绿而功能为零。修法:候选过滤走 `jsonb_array_elements_text`,名与别名
  **同一个谓词**(都用 contains),精确与否仍然只在排序层判一次。
- **LIKE 元字符未转义。** Prisma 的 `contains` 不转义,查询里带一个 `%` 就会匹配到
  调用方可见范围内的**每一个实体**。改为原生 SQL 并显式转义 `\ % _`。

另有一处是自查发现:候选截断按 `name ASC` 取前 20,「项目」这类常用词的精确命中会被
二十个字典序更靠前的部分命中挤出窗口,于是答案报 `partial` 而精确命中就躺在表里。
截断排序改为精确优先——**这是截断顺序,不是判定**,判定仍在排序层。已加探针:25 个
更靠前的部分命中之下,精确命中仍然命中。

### 8.4 `get_context` 实测:探针跑的是真代码,于是撞出一个部署级缺陷

这一轮探针**不再镜像实现**(镜像正是别名缺陷躲过去的原因),直接 `tsx` 跑
`readContext` 本身,十二项全绿:窗口含相邻章节、引用能在窗口内定位、CRLF 已归一、
radius 0 只回引用本身、文档两端 `moreBefore/moreAfter` 为假、版本失效拒绝、
无区间、非文本、字节缺失、区间越界、不可见与不存在同答。

**撞出的东西比工具本身重要**:探针改 `document.active_chunk_version` 时报
`permission denied for table document`。查下去不是探针的错——

- 列锁模型下 `karda_svc` **没有表级 UPDATE**,只有逐列授权;
- `active_chunk_version` 的授权**只在 `incr/0001` 里**,没有镜进 `98_column_locks.sql`;
- 而 `apply-local-dev.sh` 与 db-init 都**只跑基线**(`baseline → 97 → 98`),
  增量是给**已存在的库**迁移用的。

后果:**每一个已迁移的库都正常,每一个新初始化的环境都坏**——加工管道提交时的
原子切换会失败,文档永远进不了可检索状态。karda 尚未 bootstrap,所以没有环境中招,
但生产第一次 db-init 就会。已把授权补进 98,并留下 `incr/0001` 的那份给老库。

`98` 里原本的注释解释了当初为什么不能放这儿(增量加列时,98 已经跑过了)。
**那条理由在基线吸收增量的那一刻就失效了,却没人回来改。** 这类漂移旧检查看不见:
数据架构守卫比对的是表与 Prisma,不含授权。已扩为同时比对增量授权与 98,
并用这个真实缺陷验红。

`chunk` 完全没有 UPDATE 授权则是**设计正确**:chunk 不可变,重建写新版本再切换。
探针最初去改 chunk 的偏移量,是探针不对,不是库不对。

### 8.6 `browse` 实测(2026-08-26,一次性库)

十二项全绿。构造:7 条正常断言,中间夹一条 `draft`、一条无依据,另一个库再放一条。

分页翻完整库用了 3 页、取全 7 条,**跨页无重复、无遗漏**;草稿与无依据从不出现;
别的库的行从不出现;不可见库与不存在库答案完全一致;垃圾游标回到开头而不是报错。

## 9. Schema 草案

遵守 `210-data-model` 的既有约束:DDL 三段式 + 列锁 + db-init 为唯一结构变更路径;

```
karda_kb.assertion
  id              UUID PK
  kb_id           UUID NOT NULL  → knowledge_base (CASCADE)
  kind            VARCHAR(32)    CHECK IN ('fact','claim','event','procedure','rule')
  subject         VARCHAR(512)   -- 断言的主语,用于聚类与冲突候选
  statement       TEXT NOT NULL  -- 陈述本体
  asserted_by     VARCHAR(512)   -- 据谁所说(来源主体,非上传者)

  extracted_by    VARCHAR(128)   -- 过程责任:模型/管家运行,与 asserted_by 严格分开
  extraction_run  UUID           -- 可回溯到具体一次加工

  created_at / updated_at

karda_kb.span
  id              UUID PK
  document_id     UUID NOT NULL  → document (CASCADE)
  document_version INTEGER NOT NULL   -- 「哪一版」
  start_offset / end_offset  INTEGER
  excerpt         TEXT           -- 冗余存一份,重建后仍可展示

karda_kb.evidence
  id              UUID PK
  assertion_id    UUID NOT NULL  → assertion (CASCADE)
  span_id         UUID           → span (CASCADE)      -- 二者之一非空

karda_kb.assertion_mention
```

### 11.1 第 2 条改判:抽取是独立一趟,不是管线第六档(KD-211,owner 2026-08-26 落槌)

原倾向是「萃取阶段产出」,即在 `fetch/parse/chunk/embed/commit` 后面加一档。
实现抽取客户端时发现这条会付出一个不该付的代价,提请改判,同日落槌。

**决定性理由:两条管线的失效键不同。** 任务键里的 `configFingerprint` =
(模板, 参数, 嵌入模型)。抽取若同处一个任务:

- **换抽取模型 = 全量重嵌。** 指纹变了,任务键变了,整份文档从 `fetch` 重跑一遍
  ——为一个不触及任何向量的改动,重付一次 Atlas 嵌入的钱。
- **更严重:重嵌会连带重算人工裁决过的断言。** 换嵌入模型或改分块参数会让整个任务
  作废重跑,断言随之丢弃重抽。而按 KD-210,**人确认之后 confidence 不再参与排序**
  ——那些裁决是人的工作成果。让它成为一次无关配置变更的附带损失,是错的。

嵌入的失效键是向量空间,抽取的失效键是抽取模型 + 提示/模式版本。**失效键不同的两段
工作,就是两条管线**;硬塞进一个任务,等于让粗的那个键管住细的那个。

代价对比是对称的,所以不构成反驳:两种做法都要动 DDL——加第六档要放宽
`chk_processing_task_stage`,独立一趟要加任务种类。**没有哪一边能靠「不动库」取胜。**

本轮交付的客户端与 `runExtraction()` **对这条裁定完全中立**:它们接收一份文档、产出
一次事务,谁来调、什么时候调,都不影响这两个文件。

### 11.2 KD-211 的落地形状(已交付)

| | 决定 | 理由 |
|---|---|---|
| 任务种类 | `processing_task.kind` = `processing` \| `extraction` | 插入时写定,永不更新——任务不会改变物种,所以不需要 UPDATE 授权 |
| 阶段 | 抽取任务的阶段**恒为 `extract`** | 一趟是「全部窗口或一条不写」,**没有可恢复的中点**,子阶段无物可记。加工管线五档不变 |
| 工作清单 | **数据库本身**,没有内存队列 | 加工队列存在是因为上传是交互式的、有人在等;抽取无人等待。于是诚实的形状就是一条查询,重启不丢任何东西 |
| 并发唯一键 | `(document_id, kind)` 的部分唯一索引 | 原来只按 `document_id`:那条规则是为**分块原子替换的单写者**而立的,而抽取只写断言、不碰分块。不改的话,一次重加工和一次抽取会在同一份文档上互斥——一条关于分块的正确性规则,悄悄把两种无关的工作串行化了 |
| 失效驻留 | `failure_class` 新增 `unavailable` | 与 `quota` 都是驻留,**队列行为零变化**;变的是告诉运维什么。两者要求相反的动作:去催授权,还是等。对一个未授权的 `karda.extract` 说「配额」是假话,而且会是**这个增量产生的每一行**上的假话。顺带修好了 embed ——它整个 A1 等待期都被标成「配额」 |

**未抽取成功的文档也要落一行任务。** 一趟悄悄跳过它们的 pass 会永远报告
「0 份文档需要抽取」,而同一批 PDF 每一趟都被重新发现一次——那一行的作用就是让
「没有结果」这件事本身可见,并且不再被反复发现。

**驻留的必须能恢复,这一条差点写漏。** 候选查询最初是「没有任何抽取任务的文档」,
于是**驻留过的文档再也不会被看第二眼**——恰好是驻留的反面。现在 pass 先取驻留的
(复用原任务行、`attempt` 加一),再用剩余额度取新的;两者共用同一个上限,否则
持续的新上传会把驻留那一堆永远压在队尾。
