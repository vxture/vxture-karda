# 中小企业经营支撑知识体系建设策划

日期：2026-11-28。状态：B1 K1–K6＋R1/R2 已获用户批准；当前因 Karda 产品公共知识运营缺口暂缓内容建设。后续身份、运营与分发建设按 [213 批次计划](213-product-operations-public-knowledge-plan-20261128.md)，公共内容不在个人租户库先行建设。下文关于同空间 user 库先建、首期发布对象待明确的旧建议由本次决定替代。本轮未采集、入库、调用模型或发布知识。中国大陆为首期适用范围；所有具体法律、政策和解释的现行性须在实际建设时查证，本方案不构成现行法规清单。

## 1. 建设目标

建设当前智能体可以使用的通用经营支撑知识，同时以真实任务验证Karda的接入、生产、审核、图谱、版本、服务和反馈闭环。建设单位是可维护的知识产品与任务服务，不以上传文件数量或生成问答数量判完成。

先建合同与交易、用工与人事、财税与票据三个相互关联的领域；首批先把合同与交易做成可调用闭环，再逐步扩展。企业专属制度/合同/经营资料由企业授权接入，公共内容不混入某企业私有库，也不把企业数据反向写入通用内容。

现阶段使用已有本地语义配置和图谱能力，不等待Ontos、不开发本体平台，不绕过当前库权限。软件已实现不等于通用内容已可跨企业分发；当前同空间user库/OBO范围可先建设和验证，跨企业正式平台库共享需权威契约另行接入。

## 2. 分类体系：主目录与交叉标签

采用“领域 → 业务主题 → 知识条目”三级主目录，一个条目只指定一个主归属，通过标签和图谱关系跨主题复用。

| 一级领域 | 建议代码 | 二级业务主题 | 建设顺序 |
| --- | --- | --- | --- |
| 法律与合同 | LEG | 主体与授权、合同订立/效力、交付验收、付款结算、违约与解除、争议与证据、知识产权 | 第一阶段合同交易 |
| 人力资源与用工 | HR | 招聘录用、劳动合同、工时考勤休假、薪酬社保、试用与调岗、解除离职、劳务与外包 | 第二阶段 |
| 财税与资金 | FIN | 发票与凭证、费用报销、收入成本、纳税义务与申报、收付款应收、资金安排 | 第三阶段先票据与交易涉税 |
| 政策与企业办事 | POL | 企业登记、资质许可、扶持政策、申报条件、办理材料和流程 | 后续按地区选范围 |
| 销售与客户服务 | CRM | 商机与方案、客户沟通、承诺边界、服务响应、投诉与续约 | 后续企业资料结合 |
| 采购与供应商 | SCM | 准入、询比价、采购合同、交付验收、结算、供应商评价 | 随合同复用扩展 |
| 运营管理与行政 | OPS | 制度权限、项目流程、会议决策、档案、资产、行政事务 | 后续 |
| IT与数据安全 | ITD | 账号权限、系统操作、备份恢复、数据保护、AI使用、事故处置 | 后续 |

横向标签至少包括：知识性质、适用地域、行业、主体类型、规模/纳税身份等适用条件、业务环节、时间窗口、审核状态。标签取自受控词表，不把任意LLM输出直接加入分类目录。地域/效力等采用独立维度，不混入单一领域层级。

法律法规的适用性以实际条文为准，不能仅凭“中小企业”标签推断适用；企业规模、组织形式、行业、用工地点、纳税身份、交易时间等可决定结论。

## 3. 知识性质分层

| 层次 | 内容 | 管理方式 |
| --- | --- | --- |
| 原始权威来源 | 法律法规、司法解释、部门规定、官方公告与办事指南 | 保留官方原文、版本、发布机构和精确引用；来源类别不自动决定法律效力 |
| 证据化知识 | 条款要求、条件、例外、义务、期限、所需材料 | 每条关联具体条款和适用条件，机器候选经审核后发布 |
| 专业解释与实务方法 | 风险说明、审查要点、办理流程、判断方法 | 标注作者/审核者、依据、适用边界；官方解读、专业解读与平台整理分开 |
| 任务工具与模板 | 检查清单、材料清单、合同条款示例、办事步骤 | 绑定依据与版本；模板是参考，不宣称自动合法或保证审批通过 |
| 企业专属知识 | 内部制度、合同底线、审批权限、产品与客户资料 | 独立授权范围，标明企业归属；不得提升为通用法律规则 |
| 案例与经验 | 裁判案例、实践案例、企业经验 | 区分案件事实/裁判观点/经验；注明案例地位，不当作普遍适用条文 |

待验证的推断、LLM生成解释、用户反馈处于草稿/候选区，不能混入已审核知识。原文可读、知识认可、服务发布三个状态分别管理。

## 4. 物理分库策略

分类目录不等于数据库数量。按权限、发布责任、更新周期和服务对象划分物理库，主题使用目录/标签管理，不为每个主题新建一个库。

首期建议：

1. 合同交易权威来源库：首期官方原文及条款定位，保持来源权威与时效记录。
2. 合同交易实务库：经审核的审查要点、解释、流程、模板；引用来源库证据，不把经验混成原文。
3. 建设验收资料：独立隔离样例合同/待审草稿和评审记录，不对普通服务发布；若现有评测/生产草稿模块可承载，则复用而不额外新建库。
4. 企业专属库：有明确企业接入后再创建，不预先建空企业库。

后续用工、财税形成各自来源与实务治理范围，跨领域服务显式组合多个已授权库；不复制相同法规到多个库，同一条目通过稳定ID/版本及关系复用。

跨库引用的实际权限与查询支持必须验证：没有权限的依据不能因为解释条目引用它而泄露；若现有实现无法安全提供引用，先采用同权限范围内组织或标记服务不齐备，不伪造跨库关联能力。

## 5. 知识对象与最小记录规范

首期受控对象：来源文书、文书版本、条款/段落、主体、合同类型、条款主题、权利义务、触发条件、例外、期限、风险、审查项、材料、业务任务。仅建实际任务需要的对象，不追求一套包罗万象的法律本体。

建议关系：文书包含条款、版本替代版本、条款规定义务、义务受条件约束、条款存在例外、审查项依据条款、风险关联条款主题、模板适用于任务、解释引用依据、企业制度补充要求。所有自动抽取关系仍需既有审核，不用LLM自行决定效力优先级。

来源记录最低要求：

- 标题、发布机构、文号/官方标识、官方URL、来源类别、内容哈希、获取时间、可用/再利用限制。
- 发布、生效、修订、废止时间及当前状态；未知字段标未知，不填猜测值。新获取时间不等于生效时间。
- 适用地域、行业/主体条件、完整性、附件和相关版本。

知识条目最低要求：

- 稳定条目ID、主分类、业务主题、性质、表述、适用条件、例外、所需事实与不能据此回答的边界。
- 来源文书版本、条款/段落、精确原文定位；解释与模板保留依据，案例保留案件上下文。
- 草稿/待审/认可/拒绝/暂停/过期状态、作者/审核者、审核时间、更新负责人、复核触发条件。
- 地域与时间适用范围、关联审查项/任务/实体、变更记录。无法确认现行性时禁止声称“当前确定适用”。

以上先映射既有metadata、语义配置、审核与版本字段；确有结构缺口才提出最小软件变更，不为了新策划重建元数据平台。

## 6. 来源选择与建设流程

优先核查全国人大、国务院、最高人民法院、财政部、国家税务总局、人社部等官方发布渠道及适用地区官方渠道。此处为来源方向，不代表已经核验其具体URL、接口、现行文本或授权。

每个来源先登记正式URL、发布机关、当前版本、附件完整性、抓取方式和再利用条件。公开可访问不自动等于允许整库转载；法律正文、官方解读、第三方案例整理、合同模板等分别核查。避免一开始引入来源不明的付费聚合站或未经授权的模板库。

完整流程：

任务与范围定义 → 官方来源清单核查 → 原件/版本接入 → 解析与条款定位 → 候选知识/关系生成 → 适用条件与例外核对 → 专业审核 → 版本发布 → Agent任务配方绑定 → 同题验收 → 反馈与更新。

自动化承担搬运、抽取候选、版本差异与待办；有效性判断、争议解释、风险等级和正式认可有明确人类审核责任。没有专业审核资源时，首期只发布有证据的原文检索与来源说明服务；实务规则/合同审查保持待审或受限试用，不能用系统管理员身份冒充专业审阅。

## 7. 首批业务边界与交付内容

首批推荐“中国大陆企业境内一般买卖合同支撑”。先覆盖合同主体与授权、交付、质量与验收、付款、发票事项的合同约定、违约、解除、通知与证据。劳动关系、税务定性、跨境、担保、建设工程、金融等不做首批结论；识别涉及这些事项后给出明确转交/补充事实需求。

发票条款审查首期只检查合同约定及依据可追溯性，不提前作具体税率、抵扣或纳税义务判断，财税内容另批查证。

以任务驱动形成以下首批知识产品：

| 产品 | 可供智能体执行的任务 | 输出边界 |
| --- | --- | --- |
| 合同依据查询 | 根据事项查询当前已核验来源及具体条款 | 原文、时间/地域、引用与不足；不生成无证据结论 |
| 条款审查辅助 | 针对约定检查触发条件、遗漏事项与风险点 | 适用依据、合同片段、待确认事实、建议；争议事项不包装成确定结论 |
| 履约义务清单 | 整理主体、义务、条件、期限、通知与证明材料 | 区分合同约定义务、法律要求与平台建议，不凭空补期限 |

首批建议规模：8–15份核心官方来源文书（实际核查后冻结）、40–60个审核后的审查项/知识条目、20–30个代表性任务案例。数量为工作量预算，不是硬凑指标；与任务无关的文书不为了凑数入库。一个文书多版本不是多份有效知识。

首批应展示一张可解释的业务图谱：合同类型 → 条款主题 → 权利义务 → 条件/例外 → 风险/审查项 → 来源条款。节点点开可回原文和审核记录，发布视图只含当前有权读取内容，不用演示图替代真实关系。

## 8. 逐步建设批次

| 批次 | 完整交付范围 | 本次状态 |
| --- | --- | --- |
| B1 合同交易知识与服务首期 | 分类词表、来源核验接入、证据化条目/关系与审阅、三类任务服务、真实图谱、阶段验收与运行交接 | 已批准；待产品运营与分发能力就绪后恢复整体实施 |
| B2 用工与人事 | 在同一分类与治理标准下建设劳动合同、招聘入离职、工时休假等；劳动/劳务边界跨合同服务 | 后续单独计划批准 |
| B3 财税与票据 | 票据、报销和交易涉税知识，主体/纳税身份/地域/时间条件完整；与合同及用工形成组合任务 | 后续单独计划批准 |
| B4 跨领域经营支撑 | 外部人员服务、采购付款等复合任务，企业制度叠加与企业专属知识接入 | 依前三批反馈规划 |
| B5 扩展运营领域 | 政策办事、销售客服、采购供应商、运营行政、IT数据安全；按真实需求优先 | 持续演进方向，不提前建空库 |

B1按与软件建设相同的管理节奏交付，但专业审核是内容发布条件；缺审核只限制相应实务知识发布，不阻断来源接入、配置、图谱草稿、服务接线和验收工具。

## 10. 质量与更新管理

验收先看：引用是否真的支持结论、版本与地域是否适用、条件/例外是否保留、无法判断时是否明确补充事实、撤回是否停止交付。不能只看答案看起来顺畅或问答命中率。

发布门槛：

- 发布条目均有可回查依据、性质、适用条件和审核记录；来源未确认或实务未审不进入正式服务。
- 对验收集记录原始输入、实际知识引用、知识/服务版本与审核决定；开发题和用于最终判断的保留题分开，不用同批生成题自证质量。
- 每条失败记录原因：来源缺失、解析/定位、知识不足、时效/地域、适用判断、权限或服务故障；按原因修复，不把所有问题都归到检索。
- 原文依据查询可先完成软件与来源可用验收，正式法律风险判断需具备专业审核证据；系统与内容验收分别标记。

更新责任：每个知识产品有内容负责人、专业审核负责人和平台运营负责人，可由同一组织承担但职责明确。用户可以指定或委托专业审核人；AI不得替代独立专业签署。

建议运营节奏：官方来源变更检测每日一次（受站点条件/频率约束）、新增或修订先进入差异与影响队列；涉及已服务内容的生效/废止/错误应优先复核，不能等定期复盘。每月检查待审、失败抓取、未知时效和失效引用，每季度复核主题覆盖。仅在实际设置调度后才能声称自动监控已启用，本策划不创建定时任务。

知识更新流程：新版本登记 → 比较条款 → 关联审查项/服务影响 → 人工认可 → 发布新版本 → 旧知识停用或标历史 → Agent当前核验。历史用于追溯，不把“可查历史”当成“当前仍适用”。

## 11. 需在B1启动时明确的实际条件

1. 专业审核由谁承担：用户指定法务/律师，或用户安排后续专业审核。暂缺时仍可完成来源/工具与草稿建设，但不得把实务服务标正式专业认可。
2. 首期发布对象：先在现有授权工作空间验证；跨企业通用产品分发必须使用未来正式平台库权威，不通过放宽user库权限实现。
3. 具体来源清单在执行中查证后冻结；若来源数量/许可/可访问性不满足，记录可核验范围，不抓取未知来源补数。

本轮不要求先回答上述条件才能审批策划；批准B1后先推进独立工作，并在专业发布前完成必要责任确认。

## 12. 决策建议

批准总体分类和分层治理方向，下一执行对象仅为B1 K1–K6＋R1/R2。后续B2–B5不自动启动。流程保持：计划 → 批准 → 整批建设 → 阶段集中验证/专业审核 → 逐项确认 → 汇报。

全程不弹本机命令窗口，不做性能专项；没有软件改动不重复跑全量CI。本方案尚未执行入库/公开发布，也没有配置周期自动化。
