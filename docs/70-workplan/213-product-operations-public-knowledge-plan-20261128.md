## 1. 已确认的产品与身份边界

- accounts 统一认证。产品运营人员使用 workforce；租户用户使用 customer。
- admin（运营）、opera（运维）、arche（治理）是既有独立管理域；其入口权限均不自动授予 Karda 权限。
- Karda 新增独立产品运营入口和 workforce OIDC 客户端、独立会话与 cookie 命名空间；customer 客户端及租户工作台保持独立。不新建员工账户、密码或员工身份域。
- Karda 产品运营授权单独显式授予，默认无权。运营主管也不自动读取租户私有内容。授权管理与内容管理分权，编辑、审核、发布可分别授予。
- Karda 公共资产归属产品，使用产品级稳定归属标识；运营人身份记录在审计中，不成为知识所有者。不以某员工个人库或普通租户工作空间充当公共库。
- PostgreSQL 为权威数据，G6 为展示，Jena 为语义索引；沿用现有基础设施。Ontos 建模和性能专项不属于本计划。

## 6. 已批准内容批次 B1 的恢复方式

本节的“内容 B1”指 212 既有合同交易批次；软件批次 B 使用 D1–D6 编号，避免混淆。

- [ ] K1 分类与责任：合同交易来源库/实务库建立在产品公共资产下；责任与受控词表明确。
- [ ] K2 权威来源：核验官方来源、现行版本、引用定位与再利用条件，前台登记接入。
- [ ] K3 知识与关系：条件/例外/义务/风险/审查项及依据，生成候选后审阅。
- [ ] K4 Agent 服务：合同依据查询、条款审查辅助、履约义务清单三项服务配置和调用。
- [ ] K5 图谱与运营：真实合同业务图谱、原文跳转、更新影响和反馈闭环。
- [ ] K6 代表性任务：按 212 的正常/例外/缺事实/历史版本/撤回案例执行并记录。
- [ ] R1 内容与服务发布：专业审核状态决定实务服务发布范围；无代码变更不触发无意义的软件 CI。
- [ ] R2 交接：来源、条目、服务、视图、案例、待审项及维护责任清单。

所有建设默认前台人工操作；不直接写库、用脚本灌入或把租户库改成公共库。法律原文查询与专业实务审核分开；暂缺专业审核时可以完成原文服务和实务草稿，但不标正式法务认可。

## 7. 执行与汇报约定

计划 → 用户批准明确批次 → 整板块实施 → 阶段集中验证 → 按清单逐项确认 → 汇报。

每次汇报列出：本批完成项、证据、未完成项及原因、剩余批次。小改动只做必要静态检查和针对性核对；全量验证放在整板块集成后，除新增失败或变更风险需要，不重复跑全量。功能齐备优先；不以旧机器性能阻断功能建设。全程不弹出本机 CMD/PowerShell 窗口。

本次建议先批准批次 A 的 A1–A6＋R1/R2。批次 B 保留待批准；内容 B1 已批准，满足依赖后按既有授权恢复。

### 操作顺序与现有限制

/operations → 员工登录与显式授权 → 创建产品公共库 → 上传原件或登记来源文本 → 核对时效和再利用条件 → 建立并执行条款候选加工任务 → 人工编辑条目及关系（精确来源 hash＋字符区间） → 提交审核 → 独立审核人认可 → 发布人员发布 → 查看发布图谱／构建 Jena 索引 → 导出追溯记录。审核人不能审核自己参与编辑的库。

原生文本支持 TXT/Markdown、具备可提取文本的 PDF/Office；扫描 OCR 和 LLM 抽取不借用租户身份，等待明确运营调用契约。当前加工任务由前台显式执行/重试，持久记录状态；不是自动后台调度。原件保留在 product-karda 存储命名空间，未经过 tenant 用量上报；产品运营存储费用归属需后续正式计量契约，不向某客户记账。编辑器提供来源核验、证据片段预览、条件例外、关系选择等人工表单；JSON 仅保留为高级编辑入口。

客户目录、启用/订阅、消费授权和 Agent 跨租户调用仍属于待批准批次 B（D1–D6）；A 的公开发布仅表示产品内部发布版本已形成，不声称客户交付已完成。

### 数据迁移与回退

0049 仅新增独立公共运营表，不移动或更改已有个人/租户库所有权，不修改 local_authz 租户角色。基线、增量、Prisma、列授权和数据库测试声明统一112表。发布前按现有 db-init 固定提交运行；应用不自行迁移。回退应用时保留新增表和不可变发布/审计数据，运营入口保持禁用，不执行删表回滚。产品 Jena 索引使用既有内部服务和固定受限操作，构建前保存权限/发布版本围栏；撤回后的过期索引由既有清理流程回收。
