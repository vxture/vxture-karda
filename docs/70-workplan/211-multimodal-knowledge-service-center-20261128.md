# 多模态知识加工与证据服务中心实施计划

日期：2026-11-28。状态：用户已批准M1–M6＋R1/R2整体实施；开发中，尚未验证或发布。

## 1. 本批目标与产品范围

完成一个完整的软件板块：文档/图片进入平台 → 分页或分区域加工 → 形成可编辑的识别/结构化草稿 → 人工确认版本 → 进入既有知识生产审核与发布 → 页面和智能体按当前权限读取文字、图像区域、表格及视觉解释证据 → 来源或裁决变化后失效重核验。

本批首期范围明确为文档与静态视觉知识：PDF（文字、扫描、混合页）、独立PNG/JPEG、DOCX/PPTX内嵌图片、现有XLSX/DOCX/PPTX可确定读取的表格。覆盖20页以上扫描PDF，按既有来源边界支持至300页、8MiB；大文件扩容另行规划，不用硬件性能阻挡本批功能。

图表、示意图、公式同时提供原图区域证据、人工说明/结构化编辑及来源追溯。自动生成这些内容的描述或数据，只接实际有文档且已验证的Atlas能力，且始终为待审草稿；本批不把未存在的接口、通用视觉模型或自动精确读图能力写成已经具备。

Karda建设加工、治理和知识服务软件，不代建业务语料，不训练视觉模型，不开发Ontos本体平台。音视频的转写、时间轴定位、说话人识别与视频帧服务属于后续独立板块，不在本批以占位入口冒充实现。

### M1 多模态资产与定位契约

1. 输入内容校验采用实际格式与解码结果，校验图片像素/尺寸、PDF页数、压缩包展开规模；拒绝损坏、加密或超出处理范围的输入并显示原因。
2. 独立图片首期仅PNG/JPEG；保留原件，派生预览处理方向/缩放。Office提取仅已嵌入图片及已支持的原生表格，不执行宏、不外链抓图，不做Office全格式渲染承诺。
3. 视觉证据使用visualAssetId/blockId及来源库/文档/版本/哈希；定位包括PDF页码、图片/页面的归一化区域、像素尺寸与旋转变换；Office至少保留部件路径、段落/幻灯片/图片序号或工作表单元格范围，不伪造Word印刷页码。
4. 派生图片单独入对象存储，保留引用关系、存储容量统计和安全清理规则；草稿、当前版本、被发布知识引用时不可误删。
5. 旧来源文本snapshot保持不可变；新增视觉区域与文本映射通过版本化扩展承载，不就地重排历史UTF-16证据位置。

### M2 长文档与图片加工编排

1. 用户先选文档、页/区域范围与可用加工能力；系统生成冻结计划，显示总页数、已含文字、待OCR、估计调用批次数和上限，再显式启动付费加工。
2. PDF至300页，单次Atlas请求不超过其已验证20页/请求大小限制；按页分批渲染，图片及时落对象存储/释放内存，不一次加载300页base64。
3. 文字页优先复用确定性解析；扫描页进入OCR。混合页由用户显式选择补充/替换区域，避免文字与OCR重复拼接；检测置信不足可人工选择加工页。
4. 持久记录批次、页号、状态、模型/适配器版本、请求追溯、错误与usage关联；使用租约、重试上限与过期工作进程保护，避免取消后迟到结果写入。
5. 暂停停止领取新页；取消阻止新结果入当前版本，不承诺撤销已经发到模型提供方的调用。已完成页可复用，重复请求不重复提交已确认结果。
6. 提供方超时且结果不明时单列“调用结果待核对”，不宣称恰好一次计费；只有提供方支持并验证的幂等能力才用于自动重发，其他重复付费风险需用户显式重试。
7. 严格全量确认要求所选页全部处理并审阅；也可显式确认部分范围，覆盖清单列出缺失/拒绝/未处理页。部分来源不得冒充完整文档，服务返回覆盖限制。
8. 8MiB/300页或像素预算超限时显示具体边界；不进行无界渲染、自动无限重试或性能压测。

### M3 图表、公式与表格的结构化内容

1. OCR文本块保存文字、区域和阅读顺序。自动转录只是草稿，保留修订前后内容，不把模型分数解释为事实置信度。
2. 表格契约包括行列、表头、单元格值、合并范围、原始文本与来源区域/单元格位置。已有Office表格由确定性解析器复用；扫描表格可人工编辑或导入结构化草稿，只有经过验证的上游适配器才自动生成候选网格。
3. 图表/示意图提供类型、标题、图例/坐标轴/单位、人工说明和原图区域；无法可靠读取的数据点保持未知。表格值和图表说明分别审阅，不能只因图像OCR成功就标结构化识别成功。
4. 公式提供原图区域与可编辑的纯文本/LaTeX转录，标注人工/模型来源及审核状态；不执行或求解公式，不推断未识别符号。
5. 图像说明、图表解读和跨区域总结独立于精确OCR原文。没有经验证的模型输出时，完整人工编辑/导入/审阅路径仍然可用，界面明确“人工结构化”而非展示虚假自动结果。
6. 支持有界JSON草稿导入/导出，校验单元格引用、区域、页号和当前来源哈希；导入数据不自动变成正式知识，禁止跨库伪造来源。

### M4 审阅与正式知识生命周期

1. 页面/图片预览与文本、表格编辑并排，点击区域高亮，保留当前页方向和缩放；提供逐页进度、待复核筛选及键盘操作。
2. 认可/修改/拒绝及操作原因持久保存；修改生成新草稿修订，确认冻结快照，阻止并发覆盖和旧来源确认。
3. 空白页、不可辨识、后端失败、未处理分开；用户可以明确确认真实空白，但系统不能把失败直接改为空白。
4. 转录确认表示认可该版本来源表示；“图表显示某结论”等解释性断言还需进入现有知识生产中心，完成候选→审核→发布。模型输出不能自行批准事实。
5. 新版本/撤回/删除/确认被撤销时，相关图像引用、文本/单元格证据、事实与上下文按当前有效性收敛。回退仅激活仍可访问且来源兼容的版本，不恢复旧权限。
6. 原件、审阅修订、生产计划与已发布关系相互可追溯；不把识别确认等同整库生产切换。

### M5 智能体服务与多模态上下文

1. 提供按库/文档/页/视觉对象类型筛选的检索与详情读取；首期检索对象是已确认的转录、说明、表格文字及元数据。图片输入检索、视觉向量召回和跨模态重排另行选型，不冒充本批已有能力。
2. Agent返回结构化表格、原文/说明性质、来源版本、页/区域及视觉证据引用。图谱可点击回到视觉证据；不把图片二进制直接塞入图节点。
3. 扩展现有knowledge_service与任务context配方，支持显式视觉证据分区/视觉附件策略；整包保留字节、条目、图片数量/像素/字节上限，图片二进制与JSON预算分别计算。
4. 区分“当前已确认来源可读”与“其解释已正式发布”。普通原文/视觉读取不自动升级为事实；待审描述不能通过已发布服务泄露。
5. 视觉图片通过受保护的资源接口读取，每次验证当前用户/调用产品、库挂载、来源版本与权限；资源ID/URL不是授权凭据，不生成永久公开链接。若用短期凭证，必须有受众/身份绑定和当前撤权校验，不能只靠过期时间。
6. 默认返回元数据和资源引用，Agent再按需取图；在当前OBO权限下可获取适合模型输入的有界图像响应，不让外部模型匿名抓取受保护URL，不导出平台密钥。
7. 当前知识指纹、来源失效与context差异纳入视觉版本与审阅状态；历史记录不缓存可绕过权限的图片/正文。服务身份不能替代OBO取得私库资料。
8. 能力不适配、原图丢失、覆盖不全、服务停用、预算不足返回明确状态；不得静默退回纯文本却声称多模态证据齐备。沿用既有计量与追踪，避免组装层重复计费。

### M6 工作台与产品闭环

主操作路径：

知识库资料 → 选择PDF/图片/Office视觉对象 → 查看能力与覆盖情况 → 冻结加工计划 → 显式启动 → 查看逐页进度/处理失败 → 图文/表格审阅 → 确认来源版本 → 交接知识生产 → 发布审核通过的知识 → 服务与任务上下文调试 → 展开视觉证据/重新核验导出。

工作台复用已有资料/实体选择器、作业中心与知识服务配置，不再复制另一套任务引擎或发布中心。入口、按钮和错误状态具备中文/英文词条；真实无数据时显示操作引导。管理入口按当前拥有权与角色授权，消费读取仍按调用产品挂载与读权限；付费识别与导出另校验对应权限。

提供接口与接入示例、能力可用状态、任务追踪/usage、处理范围/版本说明；不要求业务人员以JSON或内部ID完成日常操作，高级导入/ID仅作为补充。

## 4. 成熟组件与技术约束

| 部分 | 首选策略 | 实施前必须确认 |
| --- | --- | --- |
| PDF文字/页码与光栅化 | 复用现有pypdf＋Poppler，扩展按页范围和持久检查点 | 运行镜像版本、许可证、页旋转/尺寸与渲染结果一致性 |
| 前端原页/区域预览 | 比较PDF.js受控渲染与既有Poppler派生图预览；优先派生图作为统一PDF/图片区域坐标底座 | PDF.js是否实际必需、包体/安全记录与许可证；不用iframe片段替代区域定位 |
| 图片解码/方向/裁剪 | 选成熟组件，优先复用运行环境已可用能力；必要时比较Sharp/libvips与Pillow | 显式运行依赖、像素上限、EXIF方向、许可证与SCA；不把构建期偶然依赖当正式运行依赖 |
| OCR与视觉模型 | 复用Atlas已发布/v1/parse OCR契约，固定任务/模型选择与usage追溯 | 能力支持、授权、错误和结果结构；不绕过Atlas直连模型，不编造图表/公式API |
| Office图片/表格 | 复用现有OOXML解析与受限ZIP读取，图片单独派生资产 | 部件关系、外链过滤、展开预算、原始定位；不新建Office套件解析器 |
| 存储、作业与服务 | PostgreSQL＋现有对象存储＋持久作业/知识生产/知识服务 | DDL、Prisma、列级授权一致，迁移可重放；旧版本读兼容、对象清理引用完整 |

本批不引入第二套图数据库、独立向量数据库或重型文档平台。新增组件先形成简明选型记录，围绕必要能力选择；在批准的本批范围内完成常规组件取舍，无需为每个可逆实现细节单独请求批准。若需要新增外部服务采购或改变产品边界，再提交具体方案。

## 5. 模型依赖与可交付性

当前仓库只有OCR请求/页与bbox的调用契约，不能据此宣称拥有完整图表理解、表格结构识别、公式识别或授权模型目录。

- 页面会明确列出OCR、结构化导入、人工编辑等实际可用能力；可读授权模型目录存在时接入，不存在时保留经服务端验证的显式模型配置和清楚的不可用状态。
- M1/M2编排、M3结构化编辑/导入、M4审核、M5知识服务和M6工作台均可通过真实存储和隔离适配器验收，不依赖真实业务语料才能开发。
- 上游没有提供自动图表解析时，该能力保持“未接入”，不以人工路径冒充自动化。自动图表/公式识别质量及真实OCR成功调用分别留证。
- 发布汇报必须区分软件交付、真实模型运行、真实外部Agent与业务效果；缺外部模型只影响对应联调结论，不能用空壳入口替代软件功能，也不能为等待接口停止其余工作。

## 6. 两项整体收尾

- [ ] R1 阶段集成与发布：M1–M6整块实现后集中完成新旧解析/证据兼容、真实数据库/对象引用、权限撤销、任务恢复、图像定位和服务调用回归；再经既有PR/主干/依赖/密钥门禁、正式迁移、部署与线上健康/拒绝核验。开发中仅必要定向检查，不逐小步全量回归，不安排性能专项，不弹本机命令窗口、不启动本地服务。
- [ ] R2 逐项确认与交接：对照M1–M6及R1/R2列实现入口、接口/文件、验证证据、格式与容量范围、依赖状态和未实现项；更新设计、使用文档、能力清单、发布/回退记录与最终勾选。最终收尾随下一批准功能PR归档，GitHub Release保留本次权威证据。

## 7. 阶段集中验收清单

1. 超过20页的扫描PDF冻结计划并分批完成；跨批次页码、区域与最终文本映射正确；恢复不丢页、不重复当前结果。
2. 混合PDF的文字页与指定OCR区域按策略处理，空白/拒绝/失败/未处理可区别；部分确认保留覆盖缺口。
3. PNG/JPEG含旋转信息时，原件/预览/裁剪区域与所示证据一致；超像素、损坏文件和来源改变明确拒绝。
