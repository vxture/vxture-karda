## 2. 运行架构

初期 Jena 采用随应用镜像交付的独立 Java 执行进程，而不是另起公开 Fuseki 服务。每个进程仅收到本次 PostgreSQL 读取器已经鉴权、过滤来源与裁决的图快照；执行标准 SHACL 和固定 SPARQL 后退出。没有数据库凭据、文件读取入口、远程 RDF、用户 SPARQL 或开放端口。RDF 内容不落盘、不写日志。

- PostgreSQL 持有权威实体、断言、证据、人审、Schema、发布 head；现有 87 表不变。
- G6 5.1.1 替换自研 SVG 画布及其在现行页面上的布局调用。旧布局/视口函数暂保留历史测试与其他引用，不再驱动该画布。
- Jena 6.3.0、Java 21：使用成熟 RDF 解析、SHACL 和 ARQ。当前不发布 inferred 关系，不宣称 OWL DL/完整 Ontos。
- 进程上限 2、20 秒外部时限、JVM 堆上限 192 MiB、2 MiB 请求/响应；固定 SPARQL 查询 5 秒、1–4 跳、最多 1,000 边。拒绝时明确不可用，不绕过 Jena 校验成功放行。
- 正式镜像内设置 KARDA_JENA_JAR/KARDA_JAVA_BINARY；生产缺失配置直接失败。未配置 Jena 的本地开发环境保留原读取路径，不标为经过 Jena 校验。
- 查询只处理调用时已授权窗口；现有 500 节点/1,000 关系返回预算保留，不声明已经完成全库图查询或容量升级。

此架构将「语义技术接入」与「全库异步持久索引」解耦。未来需要 Fuseki/TDB2 时复用稳定 IRI、RDF 格式、Schema 与同一权限契约，不改业务事实身份。

## 3. 无数据负担迁移方案

### M1：本轮应用级切换

1. 不清库、不删除旧语义表，不重写人工裁决。现有 PostgreSQL 发布就是输入权威，无需搬到第二个可写主库。
2. 镜像内预装 G6 与 Jena；正常阶段 CI、主干门禁、发布标签部署。没有新 SQL，生产 db-init 不重复执行。
3. 读取同一现行发布和当前来源，生成 RDF/SHACL并校验。RDF 指纹绑定当前图内容与约束；不是授权凭证，也不伪称为持久发布头。
4. 页面直接使用 G6。无客户数据时以合成结构完成阶段功能验证；不自动重处理客户资料、接受候选或发布事实。
5. 部署后验证版本/依赖、匿名接口拒绝和 Jar/Java 打包。真实浏览器点击与客户数据结果分别记录，不用健康探针代替。

### M2：后续持久化查询投影（先给整板块计划）

1. 由正式发布记录重建 workspace/kb/release/schemaRef 对齐的命名图与构建清单。没有数据负担时可新建空查询数据集后逐库构建，无需并行维护两套图数据库。
2. 引入 pending/building/ready/failed/superseded 状态、构建指纹、租约、错误分类和构建头 CAS；PG 与 TDB 不存在跨库 ACID，完成校验前不能切头。
3. 只有当前授权事实可以参与遍历/聚类/推导。命名图本身不是细粒度授权；不能先走私有边再过滤结果，也不能用全库推理泄露私有前提。
4. 源撤回/角色收缩/新裁决/发布变化首先阻断旧投影读取，再清理或重建。不能等待后台同步后才撤权。
5. 新增持久元数据表时按 baseline/increment/Prisma/98/210 锁步，走 db-init；本轮不提前创建空表和虚假运营状态。

### M3：回退与重建

应用回退到升级前固定版本；PG 数据和人工裁决保持。G6 是展示层替换，Jena 是派生语义执行层，均没有第二套业务写入。无需破坏性 down migration。后续 TDB/Fuseki 查询数据可从正式发布重建；备份真值优先保护 PostgreSQL 和原件对象，不能只备份图索引。
